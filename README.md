# Telegram ↔ local Codex MVP

Минимальный асинхронный Telegram-интерфейс к локальному `codex app-server`:

- long polling, без web-сервера и портов;
- доступ только для `TELEGRAM_USER_ID`;
- отдельный каталог проекта и Codex thread для каждого Telegram topic;
- продолжение thread после перезапуска через `.sessions.json`;
- независимые OpenAI и Gonka threads в каждом topic с переносом контекста при первом переходе;
- выбор модели отдельно для каждого topic;
- автоматические подтверждения обычных изменений файлов внутри topic-проекта;
- настраиваемые доверенные папки для обычных изменений файлов без подтверждения;
- approvals через зелёную и красную inline-кнопки для опасных или внешних действий;
- streaming черновика ответа в личных чатах и topics;
- постоянные Rich Messages для всех завершённых текстовых ответов Codex;
- отдельные live-карточки выполняемых команд;
- одна временная редактируемая карточка активности на каждый turn;
- изображения напрямую передаются в Codex, голосовые и аудио расшифровываются;
- консольные и файловые логи с ротацией;
- автоматическое восстановление зависшего `codex app-server`;
- исходящие подключения Telegram и Codex через локальный proxy.

## Установка

Нужны Python 3.10+, установленный `codex` в `PATH` и уже выполненный вход в Codex CLI.

```bash
codex login
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python3 -m venv .mcp-venv
.mcp-venv/bin/python -m pip install -r requirements-mcp.txt
cp .env.example .env
```

Заполните `.env`:

```dotenv
BOT_TOKEN=123456789:token_from_BotFather
TELEGRAM_USER_ID=123456789
PROJECT_DIR=/absolute/path/to/project
PROJECTS_ROOT=/absolute/path/to/telegram-projects
AGENT_TOPIC_NAME=Agent
AGENT_TOPIC_ID=
AGENT_PROJECT_DIR=/absolute/path/to/current/agent/project
AGENT_THREAD_ID=
GOOGLE_OAUTH_CLIENT_ID=
GOOGLE_OAUTH_CLIENT_SECRET=
OPENROUTER_API_KEY=
OPENROUTER_AUDIO_MODEL=google/gemini-3.5-flash-lite
PROXY_URL=socks5://127.0.0.1:2060
TELEGRAM_MAX_TOOL_RESULT_BYTES=65536
LOG_LEVEL=INFO
LOG_FILE=logs/bot.log
```

## Google Workspace MCP

Глобальные MCP-серверы `google_workspace` и `google_calendar` настраиваются в
`~/.codex/config.toml`, поэтому доступны всем локальным Codex-агентам. Первый
предоставляет только Gmail с `default_tools_approval_mode = "writes"`: чтение,
поиск и просмотр почты выполняются сразу, а отправка и изменение почты требуют
подтверждения. Второй предоставляет только Google Calendar с
`default_tools_approval_mode = "approve"`: календарные операции не показывают
карточку approval. Агент должен выполнять их только по прямой просьбе пользователя.

Обычные `fileChange`-изменения (создание и правка файлов) внутри каталога
текущего topic-проекта и добавленных через `/trustedpath` папок бот принимает
автоматически. Удаление файлов, смешанные
наборы изменений, shell-команды, MCP-операции с записью и любые изменения вне
каталога проекта по-прежнему требуют явного подтверждения в Telegram.
Отдельный `requirements-mcp.txt` включает SOCKS-зависимости для `httpx` и
`requests-oauthlib`; они нужны для Google API и обмена OAuth-кода на token через
`PROXY_URL`.

Создайте OAuth client типа Desktop application в Google Cloud, включите Gmail
API и Google Calendar API, затем заполните локальный `.env`:

```dotenv
GOOGLE_OAUTH_CLIENT_ID=...
GOOGLE_OAUTH_CLIENT_SECRET=...
```

Секреты не хранятся в `config.toml`: Codex только передаёт MCP-процессу эти две
переменные окружения. Первая авторизация выполняется в браузере; callback-порт
открывается только на время OAuth.

`PROXY_URL` передаётся HTTP-клиенту Telegram и дочернему `codex app-server` через
`HTTP_PROXY`, `HTTPS_PROXY` и `ALL_PROXY`. Поддерживаются схемы `http://`, `https://`,
`socks4://` и `socks5://`; proxy на `127.0.0.1:2060` должен быть запущен до старта
бота. Сам бот по-прежнему ничего не слушает и не открывает портов.

## Изображения и аудио

Фото и изображения, присланные как файл, скачиваются в закрытый локальный каталог
бота и передаются в `codex app-server` как `localImage`; OpenRouter для них не
используется. Файлы сохраняются, пока живёт thread, чтобы Codex мог продолжить
контекст после перезапуска.

Голосовые сообщения и аудиофайлы до 20 МБ и 10 минут локально приводятся к WAV, а
затем отправляются в OpenRouter только для расшифровки. В `.env` нужен
`OPENROUTER_API_KEY`; при желании модель задаётся через `OPENROUTER_AUDIO_MODEL`.
Расшифровка передаётся Codex обычным текстом, а исходный аудиофайл не сохраняется.
И Telegram, и OpenRouter используют `PROXY_URL`.

## Root-команды с отдельным Telegram-подтверждением

Глобальный MCP-сервер `sudo` даёт всем локальным Codex-агентам инструмент
`sudo/run_as_root`. Заявка содержит точную команду, `cwd`, лимит времени, причину,
ожидаемый результат и существенные риски. Она сначала попадает в отдельный Telegram-бот
root-подтверждений. Команда запускается от root только после кнопки «Принять» в этом
боте; кнопка «Отклонить» и отсутствие решения в течение 10 минут отменяют её.

В `~/.codex/config.toml` для одного `sudo` MCP используется режим `approve`, поэтому
Codex не показывает дублирующую карточку approval в рабочем topic. Это не означает
автоматического выполнения: фактический шлюз находится в отдельном боте.

1. Создайте отдельного бота через [@BotFather](https://t.me/BotFather) и поместите его
   токен в `.env`:

   ```dotenv
   ROOT_APPROVAL_BOT_TOKEN=...
   ROOT_APPROVAL_TELEGRAM_USER_ID=123456789
   ```

   Второе значение необязательно: пустое поле использует `TELEGRAM_USER_ID`.
2. Сначала включите approval-бот, затем установите или обновите root daemon:

   ```bash
   ./scripts/install-root-approval-bot-service.sh
   ./scripts/install-sudo-daemon.sh
   ```

   Такой порядок важен при первом переходе: старый daemon может выполнить
   установку бота, а новый начнёт принимать root-заявки только когда бот уже
   доступен для их подтверждения.

Проверка и журналы:

```bash
systemctl status codex-sudo.service codex-root-approval-bot.service
journalctl -u codex-sudo.service -u codex-root-approval-bot.service -f
```

Важно: socket по-прежнему доступен только выбранному Linux UID, а root-daemon не имеет
TCP/HTTP-порта. Это не защита от скомпрометированного Linux-аккаунта того же UID:
такой процесс уже может обращаться к socket. Не используйте сервис в общей учётной
записи и не одобряйте команду, которую вы не прочитали целиком.

## Автозапуск systemd

`xray.service` обслуживает `127.0.0.1:2060`, `codex-sudo.service` — Unix socket
root-инструмента, `codex-root-approval-bot.service` — отдельного бота подтверждений,
а `telegram-codex.service` запускает рабочий бот от обычного Linux-пользователя. Он
ждёт доступность proxy, перезапускается после ошибок, корректно завершает
`codex app-server` и стартует после перезагрузки до входа в графическую сессию.

Установите unit:

```bash
./scripts/install-telegram-codex-service.sh
```

Установщик сам останавливает прежний bot-процесс из tmux (не закрывая остальные окна),
чтобы два long-polling процесса одного бота не конфликтовали.

Проверка и логи:

```bash
systemctl status xray.service codex-sudo.service codex-root-approval-bot.service telegram-codex.service
journalctl -u telegram-codex.service -f
```

`/restart` остаётся рабочей: он заменяет процесс внутри того же unit. Удаление
автозапуска: `./scripts/uninstall-telegram-codex-service.sh`.

`PROJECT_DIR` используется в основном чате без topic. Каждый topic получает отдельный
каталог внутри `PROJECTS_ROOT`. Если `PROJECTS_ROOT` не указан, используется
`PROJECT_DIR/.telegram-codex-projects`.

Topic с именем `AGENT_TOPIC_NAME` всегда использует `AGENT_PROJECT_DIR`. Для уже
существующего topic можно также указать его числовой `AGENT_TOPIC_ID`: тогда
привязка сохранится даже после переименования. Его Codex thread хранится в
`.sessions.json` и продолжается после перезапуска, как обычно.

`AGENT_THREAD_ID` позволяет явно закрепить конкретный сохранённый Codex thread.
Оставляйте поле пустым, если тот же thread одновременно открыт в другом процессе
Codex: параллельная запись двумя `app-server` не является поддержанным способом
совместной работы и может повредить последовательность событий. Без этого параметра
topic получает собственный долговечный thread в том же проекте.

## Включение topics

В личном чате откройте Mini App [@BotFather](https://t.me/BotFather), выберите бота
и включите `Topics` и `Allow users to create topics`. После этого создавайте topic
обычной кнопкой интерфейса Telegram — писать `/topic` не требуется. Бот обработает
служебное сообщение `forum_topic_created` и автоматически создаст отдельный каталог
и Codex thread. То же работает для topic, созданного пользователем в forum
supergroup. Команда `/topic <имя>` оставлена как необязательный запасной вариант;
для неё боту нужно право `can_manage_topics`.

## Запуск

```bash
source .venv/bin/activate
python bot.py
```

Команды:

- `/start` — состояние topics, проекта и быстрый выбор модели;
- `/project` — показать каталог и thread текущего topic;
- `/provider` — выбрать OpenAI Codex или Gonka для текущего topic. У каждого провайдера свой нативный thread; при первом переходе следующий запрос получает компактную выжимку истории topic;
- `/model` — показать актуальные модели из `codex app-server` и выбрать модель topic;
- `/new` — заменить Codex thread, сохранив каталог проекта;
- `/stop` — отменить approvals, отправить interrupt и дождаться подтверждения Codex.
- `/fullaccess 15` — дать всем агентам полный доступ обычного Linux-пользователя на 15 минут; также доступны `/fullaccess 60`, `/fullaccess 240`, `/fullaccess status` и `/fullaccess off`. Root-команды не входят в этот режим и остаются за отдельным root-ботом.
- `/trustedpath` — список дополнительных папок, где создание и изменение файлов допускаются без подтверждения. Добавление: `/trustedpath add /абсолютный/путь`; удаление: `/trustedpath remove /абсолютный/путь`. Папка должна существовать и быть доступна пользователю бота для записи. Удаления файлов, shell-команды, MCP-записи и root-команды в это правило не входят.
- `/restart` — полностью перезапустить бота и `codex app-server` в текущем tmux.

Если в topic уже идёт turn, новое сообщение не теряется: бот показывает кнопки
«Отправить сейчас» (прервать текущий turn и выполнить новое сообщение первым) и
«Добавить в очередь» (выполнить после текущего turn). Очередь отдельная для каждого
chat/topic; фото, изображения и аудио после подготовки используют тот же механизм.

## Провайдеры и модели

`/provider` запускает отдельный `codex app-server` для выбранного провайдера. Для
Gonka бот читает существующий профиль `~/.codex/gonka.config.toml` и передаёт его
настройки как поддерживаемые `--config` параметры: в актуальном Codex CLI сам
`--profile` недоступен у `app-server`. В picker Gonka намеренно показываются только
`gonka-minimax`, `gonka-deepseek` и `gonka-kimi`, чтобы OpenAI-модели нельзя было
случайно отправить через Gonka bridge.

Чтобы добавить следующий провайдер, создайте отдельный профиль в `~/.codex`, затем
добавьте его id, название, имя профиля и допустимые модели в `PROVIDERS` в `bot.py`.
Такой провайдер автоматически получит изолированный app-server и сохранённый thread
для каждого topic.

Скрытый fallback `/topic <имя>` тоже поддерживается, но при включённом нативном
создании topics он не нужен.

В private chat streaming выполняется через `sendMessageDraft`; черновик временный,
но каждый завершённый текстовый `agentMessage` сразу отправляется постоянным Rich
Message и больше не редактируется. Обновления плана используют отдельный Rich Message:
новая версия заменяет предыдущую в пределах turn. Служебные события не засоряют
topic: поиск, MCP-вызовы и текущий reasoning сменяют друг друга в одной временной
карточке; reasoning показывается в сворачиваемой цитате, а после успешного завершения
карточка удаляется. Ошибки и список изменённых файлов остаются. Каждая команда
остаётся отдельной: при запуске виден её полный текст, затем та же карточка обновляется
статусом, exit code и кратким выводом.
Approval после нажатия также редактируется и сохраняет принятое решение.
Длинные Google OAuth URL отправляются отдельной inline-кнопкой, чтобы Telegram
не изменял параметры ссылки при обработке Rich Markdown.

Чтобы получать обычные сообщения в supergroup, сделайте бота администратором или
отключите ему Privacy Mode через BotFather (`/setprivacy`). Обрабатывать команды и
approvals по-прежнему сможет только пользователь с заданным `TELEGRAM_USER_ID`, но
ответы, отправленные в группу, видны её участникам; для приватной работы используйте
личный чат.

`/stop` не сообщает об успешной остановке до события `turn/completed`. Пока Codex не
подтвердил завершение, новые задачи и `/new` заблокированы. Thread при остановке не
удаляется. `/new` начинает новый thread только для текущего чата/topic. Выбранная
модель и состояние сохраняются локально в `.sessions.json`.

Если app-server не отвечает на JSON-RPC, бот завершает всю его process group,
включая зависшие `codex-code-mode-host`, запускает новый app-server и повторно
подключает сохранённые threads. Запрос пользователя после такого восстановления
повторяется один раз. Если `turn/completed` не пришёл после `/stop`, восстановление
также выполняется автоматически. `/restart` аккуратно останавливает polling,
сохраняет sessions, закрывает процессы и заменяет текущий Python-процесс через
`exec`, поэтому tmux-панель и команда запуска не меняются.

Лог одновременно пишется в stderr и `LOG_FILE`. Файл ограничен 5 МиБ, хранится до
пяти архивов. На уровне `INFO` записываются запуск и остановка процессов, topic,
thread/turn, модели, approvals, инструменты, изменения файлов и все выполняемые
команды с cwd, статусом и exit code. Токен и полный текст пользовательских сообщений
не логируются. Для диагностики JSON-RPC установите `LOG_LEVEL=DEBUG`.
