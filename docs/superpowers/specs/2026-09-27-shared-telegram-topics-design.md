# Общие топики в личных чатах Telegram

Дата: 2026-09-27

## Цель и границы

Владелец бота может дать другому пользователю доступ к конкретному топику своего личного чата с ботом. У приглашённого появляется отдельный топик в его личном чате с тем же ботом. Новые сообщения участников и ответы агента отображаются в обоих топиках, а запросы обоих участников идут в одну Codex-сессию и один проект. Агент получает явную метку автора каждого человеческого сообщения. История до подключения гостя не переносится. Существующие несвязанные топики и сессии сохраняют прежнее поведение.

Гость может отправлять обычные задачи и поддерживаемые медиа, но не может управлять моделью, провайдером, каталогом проекта, полнотой доступа, остановкой, напоминаниями, приглашениями или подтверждениями действий. Все такие команды, callback-кнопки и подтверждения остаются только у владельца (`TELEGRAM_USER_ID`). Если задача гостя вызывает запрос подтверждения, решение принимает владелец. Включённый владельцем режим полного доступа не должен автоматически обходить подтверждение для действий, инициированных гостем.

## Ограничения Telegram

Bot API позволяет боту создавать топики в личном чате с пользователем и отправлять сообщения в конкретный `message_thread_id`, если у бота включён режим Topics. Бот не может первым начать личный чат: для нового пользователя нужен `/start`. `KeyboardButtonRequestUsers` передаёт устойчивый ID выбранного человека, но сам по себе не даёт боту права ему написать. Произвольный приватный чат нельзя надёжно найти по одному `@username`. Поэтому неизвестный боту username не превращается в доступ без явного открытия приглашения.

Источники: [Bot API](https://core.telegram.org/bots/api), [Bot Features и deep linking](https://core.telegram.org/bots/features), [Bot API changelog](https://core.telegram.org/bots/api-changelog).

## Приглашения и отзыв

- `/share` в топике владельца создаёт одноразовую ссылку `https://t.me/<bot>?start=<token>`. Токен криптографически случайный, ограничен по сроку (семь суток), хранится только в виде хеша и погашается атомарно при подключении. Ссылку может принять первый открывший её пользователь, кроме владельца. В ответе владельцу явно говорится, что ссылку нельзя публиковать открыто.
- `/share @username` приглашает напрямую, только если этот username однозначно сопоставлен с Telegram ID, который бот ранее увидел в личном общении **после внедрения реестра пользователей**. Перед отправкой бот проверяет доступность чата. Для неизвестного username бот выдаёт одноразовую ссылку и поясняет, что её нужно передать адресату; потенциальное совпадение username на будущем `/start` само по себе не выдаёт доступ, поскольку username изменяем. Старые контакты бот не может восстановить из истории Bot API; для них подходят выбор пользователя или ссылка.
- Кнопка «Выбрать пользователя» в личном чате владельца использует `KeyboardButtonRequestUsers` и привязывает приглашение к стабильному ID. Если бот уже может написать человеку, он создаёт топик и уведомляет сразу. Иначе приглашение сохраняется по ID и активируется при `/start` этого ID. `request_id` связан с исходным топиком, чтобы ответ на старую кнопку не пригласил человека в другой топик.
- При `/start` гость получает список ожидающих приглашений по ID и возможность открыть соответствующие топики. Ссылка обрабатывается тем же обработчиком. Неавторизованный `/start` не создаёт Codex-сессию и не открывает владельческий проект.
- Повторное приглашение того же ID в тот же топик идемпотентно. Один владелец может пригласить несколько гостей в один топик; каждый получает свой личный топик и все новые сообщения участников.
- `/unshare` владельца показывает участников текущего топика или удаляет доступ указанного ID/@username. Неоднозначный username требует выбора ID. Отзыв немедленно запрещает входящие сообщения из гостевого топика и прекращает доставку туда; уже отправленные сообщения физически остаются в Telegram. Все ещё не использованные ссылки данного общего топика при отзыве инвалидируются, чтобы отозванный участник не смог вернуться по старой ссылке. Гостю и владельцу направляется уведомление, если их чаты доступны.

## Сессии, данные и поток сообщений

Существующий `Session` остаётся каноническим и принадлежит топику владельца. Отдельный реестр общих топиков хранит соответствие `guest TopicKey -> owner TopicKey`, членство по устойчивому `user_id`, известные боту приватные контакты, ожидающие приглашения и хеши ссылок. Реестр сохраняется атомарно в отдельном локальном JSON-файле; загрузка проверяет схему, допустимые ID и отсутствие двойной привязки гостевого топика. Секретные значения ссылок не журналируются. Создание топика и сохранение привязки выполняются так, чтобы повторный `/start` после сбоя не создавал вторую Codex-сессию; частично выполненное приглашение можно безопасно повторить.

Для входящего сообщения авторизация идёт до выбора сессии. Только владелец в своём топике или участник в привязанном личном топике могут отправить задачу. Внутренний объект входа содержит стабильный ID, отображаемое имя, роль владельца/гостя и исходный `TopicKey`. Текст для агента получает явно отделённую метку автора, сформированную ботом, а не доверенную сообщением пользователя. Очередь и блокировка канонической сессии сохраняют порядок задач. Поддерживаемые текст, фото, документы и голосовые/аудио сообщения зеркалируются всем другим участникам; для медиа используется `copyMessage` в нужный топик и отдельная видимая метка автора. Неподдерживаемый тип получает явное сообщение об ошибке отправителю, без запуска пустой задачи.

Ответы, ошибки и содержательные статусы агента рассылаются во все подключённые топики. Для редактируемых статусных сообщений и live-представления хранится отдельный `message_id` на получателя; ошибка одной копии не мешает остальным. Личные ответы на команды управления и интерактивные меню не зеркалируются. Карточка запроса подтверждения с действующими кнопками отправляется только владельцу; гостям показывается текстовый статус ожидания владельца и итог решения без кнопок. Любые callback-данные проверяются по Telegram ID владельца и каноническому топику, даже если кто-то получил копию кнопки.

Новые сообщения зеркалируются с момента фактического подключения. Старые сообщения не выгружаются; удаления Telegram не сообщает боту как универсальное собы, поэтому удаление исходного сообщения не удаляет копии. Редактирование человеческого сообщения зеркалируется, когда бот получает соответствующий `edited_message` и обе копии ещё доступны. Эти ограничения указываются в тексте `/share`.

## Ошибки и безопасность

Ошибка `bot was blocked`, недоступный чат или удалённый топик превращают участника в состояние «доставка недоступна»: другие участники и Codex-сессия продолжают работать, владелец получает одно уведомление о сбое без спама. При следующем `/start` доступный топик восстанавливается либо создаётся вновь после проверки членства. Временные ошибки и `retry_after` повторяются ограниченное число раз; ошибки доставки пишутся в лог без токенов и содержимого приватных файлов. Бот не обещает доставку сообщений, которые Telegram отверг во время блокировки: после восстановления показывает предупреждение о возможном пропуске.

Любое сообщение гостя вне привязанного топика не попадает в проект. Все команды и callback-обработчики проверяют права централизованно; отдельный тест защищает от обхода через старую inline-кнопку, сервисное событие, прямую команду или неизвестный тип update. Метка автора использует устойчивый ID для логики; имя и username — только для отображения и не дают прав. Владелец должен понимать, что приглашённый видит все **новые** ответы агента в общем топике, включая потенциально чувствительный текст, который агент туда выводит.

## Проверка

Автоматические тесты покрывают: ссылку и повторное/просроченное погашение; известный ID и ожидающий `/start`; неизвестный username; выбор пользователя; идемпотентность; несколько гостей; перезапуск между приглашением и подключением; единый `Session`/проект/очередь; метки авторов; текст и поддерживаемые медиа; отзыв; отсутствие гостевых команд и callback-подтверждений; запрос подтверждения от гостевой задачи; ошибки создания топика, блокировки, временной доставки и восстановления; несвязанные существующие топики. После реализации выполняются тесты проекта и проверка запуска/загрузки состояния. Живую проверку с реальным гостем проводят только при наличии добровольного тестового аккаунта; код не рассылает приглашения реальным людям сам по себе.
